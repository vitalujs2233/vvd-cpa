# Производственные покупки IPv4, ISP и Mobile

Реализован обычный purchase без control_id и без индивидуального permit.
Это тот же реальный баланс инструментов, POST /order и GET /get/proxies, которые
использует существующая интеграция. В production нет имитированного поставщика,
тестовых зачислений или автоматического создания разрешений.

## Выполненные программные условия

| Область | Реализация |
| --- | --- |
| Баланс и резерв | Проверка реальной доступной суммы и refund_debt; резерв, baseline ID, стоимость поставщика, основание допуска и submitting фиксируются атомарно до POST. |
| Повторные запросы | UUID заказа, блокировка типа и владельца, статус submitting/uncertain, уникальный supplier receipt и финансовая транзакция исключают повторный POST и списание. |
| Ответ поставщика | Проверяются success, непустой допустимый orderNumber, валюта/тип при наличии. Подтверждённый receipt сохраняется до завершения учёта. |
| Восстановление учёта | При сохранённом подтверждённом receipt worker завершает прежнее списание резерва без повторного POST; пишет payment_recovered. |
| Неизвестный результат | Резерв и очередь сохраняются; после срока ожидания — ручная сверка. Ни таймаут, ни пустой инвентарь не означают отказ. |
| Подтверждённый отказ/возврат | Существующий authorized financial-resolution проверяет исходную сумму/receipt, окончательность отказа и отсутствие будущей выдачи; возврат и аудит атомарны и идемпотентны. |
| Принадлежность товара | Сохранённое подтверждение выделенного аккаунта; сравнение ID, точного количества, страны, срока; для Mobile оператора и ротации; отсутствие чужих claims и исторических конфликтов. |
| Фоновая выдача | Worker выбирает обычные производственные заказы без permit; состояние и основание допуска в PostgreSQL переживают перезапуск и остановку новых продаж. |
| Интерфейс | PR91: выбор → расчёт → Купить → сохранённый заказ → подтверждение суммы → обработка → автоматическая выдача в «Мои прокси». После допуска сервер показывает обычную покупку без контрольной кнопки. |

## Активация после отдельной финансовой приёмки

При поставке этих изменений настройки **не активируются**. Миграция добавляет
nullable fulfillment_authority и индекс; старым заказам допуск не присваивается,
балансы и существующие разрешения не меняются.

Для включения владелец должен подтвердить финансовую приёмку и отдельно разрешить
обычные операции нужных типов. После этого уполномоченный оператор задаёт на Render:

- существующий `PROXY_IPV4_PURCHASES_ENABLED=true`;
- `PROXY_IPV4_PRODUCTION_TYPES` — только согласованные типы из `ipv4,isp,mobile`;
- `PROXY_IPV4_EXCLUSIVE_ACCOUNT_CONFIRMED=true` — подтверждённое отсутствие иных
  клиентов и ручных покупок на аккаунте поставщика;
- `PROXY_IPV4_FINANCIAL_ACCEPTANCE_REF` — реальная ссылка/идентификатор утверждённой
  финансовой приёмки (3–120 символов A–Z/a–z/0–9 и `_.:/#-`), не фиктивное значение.

Отсутствие любого условия оставляет новые производственные покупки закрытыми.
Настройка типов не изменяет IPv6. После deploy `/checkout-config` сообщает
допущенные типы, а startup-лог `Proxy production purchase types` перечисляет их
без секретов. Никаких изменений frontend для активации не требуется.

Для остановки новых операций очистить PROXY_IPV4_PRODUCTION_TYPES и развернуть
конфигурацию. Уже отправленные заказы продолжают безопасное получение товара по
сохранённому основанию; нельзя удалять их резервы, baseline или историю назначения.
Выделенный аккаунт должен оставаться выделенным и после остановки новых продаж.

## Финансовая приёмка и реальные операции

Программные пути реализованы; реальное списание и реальные непустые ответы/подключение
поставщика ещё не подтверждены платной операцией. Эта запись не подменяет финансовую
приёмку владельца и не разрешает включение продаж.

Для приёмки сверяют исходную цену покупателя, сохранённую стоимость поставщика,
резерв, orderNumber и финансовый журнал. Успех — ровно одно списание согласованной
цены и назначение полного подтверждённого набора ID. При неопределённости новый POST
запрещён; решение принимают после фактической сверки с поставщиком. Процедура
paid/rejected/refunded и обязательные доказательства описаны в
[PROXY_CONTROLLED_CHECKOUT.md](PROXY_CONTROLLED_CHECKOUT.md).

Проверки изменений запускаются в существующем CI, изолированно от production.
Ветка `PROXY_TEST_MODE=production` вызывает обычный purchase без control_id,
проверяет ноль permits, резерв, финансовое завершение и автоматическую выдачу
для каждого типа. Это регрессионная проверка производственного кода, а не
пользовательский демонстрационный режим и не подтверждение реального платежа.
