# Протокол независимой проверки одной платной операции

Статус: проект процедуры, НЕ разрешение на покупку. Владелец 26.10.2026 подтвердил:
аккаунт Proxy-IPv4 выделен исключительно VVD CPA, сторонних покупок/API-клиентов нет
и не будет. Повторно доказывать это условие общим аудитом не требуется; нарушение
условия в будущем останавливает проверку и последующие покупки.

## Воспроизводимая бесплатная проверка

Запустить GitHub Actions **Proxy controlled verification process** (workflow_dispatch).
Workflow сам создаёт одноразовый PostgreSQL 17 `proxy_verification_test` на localhost;
production Supabase не используется. Секрет Proxy-IPv4 отсутствует. Скрипт
`scripts/proxy_verification_process.py` дополнительно отказывается работать с другой
БД или при наличии ключа поставщика. Сетевой транспорт поставщика заблокирован.

Для каждого из IPv4, ISP, Mobile реальные функции prepare/purchase/review/approve/
order_proxies работают с отдельным тестовым пользователем и кошельком. Подменены
только Telegram identity/admin verification и ответы поставщика. Production allowlist
покупок изменяется только временным mock внутри тестового процесса.

Сценарий: 100.00 тестовых USD -> prepared -> reserved (66.20 available / 33.80
reserved, это проверяется внутри вызова fake supplier) -> один успешный ответ с
фиктивным orderNumber -> 66.20 / 0.00. Затем время сдвигается в БД, без реального
ожидания: задержка 90 секунд, частичная выдача 1/2, таймаут 16 минут, перезапуск
соединений, полный набор 2/2 без разрешения выдачи, административное подтверждение
ссылкой `mock-only:dedicated-account`, выдача ровно двух ID. Повтор purchase не создаёт
ни второго обращения поставщику, ни второго финансового списания.

Отдельный сценарий: поставщик принял запрос, транспорт вернул TimeoutError. Повторные
запросы не вызывают поставщика; available=66.20, reserved=33.80; пользователю не
выдаётся прокси и не показывается успешная оплата.

JSON, сформированный backend-обработчиками, передаётся настоящему компоненту
`ProxyOrders` через тестовый адаптер marketApi. Playwright проверяет 18 состояний:
до подтверждения нет карточек подключения; после него отображаются два фактически
возвращённых тестовым backend адреса. Это сквозной тест данных backend -> UI, а не
проверка HTTP/Telegram-аутентификации или реальной сети поставщика. Артефакт
`proxy-controlled-process` содержит JSON и три снимка экрана, только с fake данными.
Он не включён в production entry point или Vite build.

## Бесплатная проверка живого API

При старте backend один раз на процесс выполняются только:
`GET /get/proxies?proxyType=ipv4`, затем `isp`, затем `mobile`.
Существующий provider использует существующий ключ внутри Render. Диагностика
`Proxy inventory schema` содержит success, количество, типы пяти требуемых полей,
число некорректных/повторяющихся ID, принимаются ли даты парсером PR #87 и являются
ли интервалы положительными целыми сутками. Значения ID, IP, логины, пароли,
rebootLink, ключ и исходный ответ не журналируются. БД и кошельки не меняются.

Пустой список с success=true доказывает доступность маршрута и отсутствие записей
в ответе. Он НЕ доказывает формат ID/дат/оператора/ротации. Не создавать платный заказ
ради заполнения этой проверки без отдельного разрешения. Непустой ответ анализируется
в памяти; при несовместимости сохранять запрет выдачи и исправлять только подтверждённый
формат. Не приписывать датам без timezone выдуманный часовой пояс.

## Перед единственной платной операцией

1. Зафиксировать точный commit, оператора проверки и независимого проверяющего,
   внутренний UUID/request_id, продукт, страну, срок, количество, для Mobile — оператор
   и ротацию. Получить свежую цену и согласовать точный максимальный расход USD.
2. Получить отдельное явное разрешение владельца именно на этот заказ/цену/тип.
   Массовый allowlist IPv4/ISP/Mobile не включать. До выполнения должен быть проверен
   отдельный механизм разрешения одной операции, привязанный к UUID; его сейчас нет.
3. Использовать выделенного реального тестового покупателя и законно зачисленные
   средства. Не пополнять его прямым UPDATE и не использовать баланс чужого пользователя.
4. Убедиться, что нет reserved/submitting/uncertain или fulfilled без approved
   предыдущего заказа того же типа. Снять полный снимок уникальных ID под общей
   межпроцессной блокировкой и сохранить его до POST /order.
5. До POST подтвердить применимую финансовую процедуру ниже и ответственного за
   ручную сверку. Записать исходные available/reserved, цену, snapshot и время.

## Выполнение и критерии успеха

- Один POST /order; до запроса в БД уже есть резерв, submitting, snapshot и время.
- Сохранить orderNumber. Сетевой таймаут или невалидный ответ — uncertain, без ретрая.
- Опрос только GET /get/proxies того же типа. Задержка более минуты допустима.
- Частичный набор не выдавать. После 15 минут перевести на ручную проверку, не
  освобождать очередь, не повторять POST и не возвращать резерв по одному таймауту.
- Успех: подтверждённый supplier receipt; ровно заказанное количество новых уникальных
  ID; страна и dateEnd-dateStart совпадают; Mobile operator/rotation совпадают;
  нет потерянных baseline/candidate ID, лишних записей, исторических конфликтов или
  назначений другому заказу; все данные подключения полноценны.
- Администратор повторно читает инвентарь и подтверждает exact candidate_ids через
  существующий approve API со ссылкой на независимые доказательства. Записываются
  review, assignments и аудит. Проверяющий открывает «Мои прокси» именно покупателя.
- Ровно одна purchase-транзакция на orderNumber, один расход резерва, повторный запрос
  возвращает прежний результат; другой пользователь не получает данные заказа.
- Проверить реальную работоспособность выданного подключения отдельным безопасным
  запросом через прокси, не публикуя credentials. Этот этап НЕ покрывается mock-тестом.

## Финансовая сверка при неопределённости

Ответственный администратор собирает ticket/выписку поставщика, orderNumber,
заявленный результат и сумму, сведения о debit/refund поставщика, UUID/request_id,
статусы/кошелёк/транзакции до и после. Не помещать credentials в отчёт. Второй
проверяющий подтверждает соответствие одного supplier receipt одному внутреннему
заказу. Совпадение инвентаря или отсутствие прокси не доказывает отказ/возврат денег.

| Доказанный результат | Действие |
| --- | --- |
| Поставщик подтвердил успешный заказ, внутренний статус submitting/uncertain | Существующий `confirm_fulfilled(owner, UUID, orderNumber)` атомарно расходует резерв и пишет одну purchase-транзакцию; повтор с тем же номером идемпотентен. Проверить уникальность receipt и сумму. Это НЕ подтверждает принадлежность прокси: затем отдельная сверка выдачи. |
| Отправки поставщику точно не было, статус reserved | `release_reservation` разрешён только до submitting; повтор cancelled не меняет баланс. |
| После submitting поставщик документально подтвердил отказ/отмену без будущей выдачи и отсутствие списания либо завершённый возврат | Нужна отдельно проверенная атомарная операция возврата для proxy intents: блокировка заказа и кошелька, проверка старого статуса/суммы/доказательства, уникальный ключ решения, уменьшение reserved и увеличение available ровно один раз, закрытие заказа и аудит в одной транзакции. Такой операции в текущем proxy wallet нет; существующий release_reservation для этого применять запрещено. До её реализации и проверки платный запуск не разрешать. |
| Заказ уже fulfilled, но поставщик затем вернул деньги | Нужна отдельная идемпотентная компенсирующая refund-транзакция с доказательством возврата; не повторный расход/освобождение reserved. Текущая delivery-admin API этого не делает. |
| Результат неизвестен / противоречив / support не ответил | Сохранить резерв (если ещё не списан), статус проверки и блокировку типа. Никаких автоматических покупок, возвратов и принудительной выдачи. |

Все финансовые действия требуют предварительного dry-run на копии тестового состояния,
сверки точных сумм, полномочий и неизменяемого аудита. Этот документ не даёт разрешения
на прямой SQL или изменение реального баланса. Пока отсутствуют подтверждённая процедура
отказа/возврата и ограничитель одной операции, реальную платную проверку не проводить.

тип/страна/срок/количество, UUID/request_id/orderNumber, baseline и выданные ID в закрытом
журнале, пройденные/непройденные проверки, available/reserved и ledger до/после, число
