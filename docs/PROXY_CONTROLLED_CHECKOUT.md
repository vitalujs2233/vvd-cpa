# Контрольная покупка: реализованный процесс

Покупка НЕ разрешена этим документом. Разработка не создаёт разрешений и не меняет
балансы. Массовый allowlist остаётся IPv6-only. Перед развёртыванием применить
`supabase/migrations/20261026125133_proxy_controlled_checkout.sql` (две пустые таблицы,
RLS и запрет anon/authenticated); затем backend и frontend одной версии.

## Что теперь делает код

- Одноразовое разрешение связано с внутренним UUID заказа и отдельным permit UUID,
  USD-лимитом, сроком до часа, администратором, evidence_ref и подтверждением выделенного
  аккаунта. Создание разрешения само по себе ничего не покупает.
- Пользователь подтверждает покупку своего заказа. Цена пересчитывается. Под общей
  блокировкой типа снимается baseline ID. В одной транзакции расходуется permit,
  резервируются средства и записываются submitting/baseline/время/стоимость поставщика.
  После commit выполняется ровно один POST /order. При потере процесса это состояние
  запрещает повторную отправку даже если неизвестно, дошёл ли POST.
- Переиспользовать permit для другого UUID/пользователя, после срока/отзыва, сверх
  лимита или после отправки нельзя. Разрешение не меняет общий флаг продаж.
- Фоновый процесс раз в 10 секунд восстанавливает работу из БД; работает без открытой
  Mini App. Он никогда не покупает повторно и не возвращает деньги по таймауту.
- Полный точный набор автоматически назначается и виден в «Мои прокси»: ID, count,
  country, dateEnd-dateStart, Mobile operator/rotation, время начала, отсутствие чужих
  назначений и сохранённых конфликтов. Связь с выделенным аккаунтом зафиксирована в
  разрешении. До полного подтверждения credentials не выдаются.
- Через 15 минут — manual_review, блокировка типа сохраняется. Поздний полный набор
  после эскалации требует существующего административного approve, не нового POST.
- PostgreSQL per-type advisory lock, FOR UPDATE и уникальные constraints защищают
  несколько backend-процессов. Неизвестная оплата сохраняет резерв; повреждённый или
  неоднозначный инвентарь не выпускает очередь.

## Подготовка без покупки

В «Прокси» выбрать параметры, рассчитать цену и нажать **Купить**. Откроется
«Мои прокси» с подготовленным заказом, UUID и суммой. Это единый вход в оформление;
финансовое подтверждение выполняется отдельно в карточке заказа.
Это не резервирует деньги. Владелец отдельно разрешает конкретный UUID и максимальную
сумму. Никаких разрешений на этом этапе разработки не создано.

Все административные вызовы используют действительный `X-Telegram-Init-Data`
администратора (существующая проверка Telegram + admin role), не API-ключ поставщика.

`POST /tools-market/proxy-ipv4/admin/orders/{order_uuid}/control-permit`

```json
{
  "permit_id":"<новый UUID>",
  "max_amount_usd":"<согласованный лимит>",
  "expires_at":"<будущее время ISO 8601 с timezone, не дальше часа>",
  "exclusive_account_confirmed":true,
  "evidence_ref":"approval:<ссылка-на-разрешение-владельца>"
}
```

Повтор того же тела идемпотентен. Иной permit для того же заказа запрещён.
`DELETE .../{order_uuid}/control-permit` отзывает только ещё не использованный permit.
Для нового разрешения после отзыва/истечения подготовить новый заказ; старый не покупать.

После обновления «Мои прокси» только у разрешённого заказа появляется кнопка
**Контрольная покупка за $...**. Клиент передаёт `control_id` в существующий purchase
endpoint; сервер независимо проверяет permit, владельца и сумму. Обычные кнопки
массовых покупок трёх типов заблокированы. При ошибке не создавать новую покупку:
смотреть текущий статус. Можно закрыть приложение: выдачу продолжает backend.

## Финансовая сверка — теперь реализована

`POST /tools-market/proxy-ipv4/admin/orders/{order_uuid}/financial-resolution`

```json
{
  "decision_id":"<новый UUID решения>",
  "outcome":"paid | rejected | refunded",
  "provider_order_id":"<подтверждённый orderNumber; можно null только если его нет при отказе>",
  "confirmed_provider_amount":"<точная исходная стоимость заказа поставщика USD>",
  "supplier_final_confirmed":true,
  "no_future_delivery_confirmed":true,
  "evidence_ref":"support:<проверенный-документ-поставщика>"
}
```

Поле confirmed_provider_amount — исходная supplier cost, не произвольная сумма
возврата и не customer price. Сервер сравнивает его с сохранённой стоимостью.
Возвращаемую сумму сервер берёт только из quoted_amount. Действие разрешено лишь
после независимой проверки evidence; отсутствие товара и таймаут не являются отказом.

| outcome | Допустимый исходный статус | Атомарный результат |
| --- | --- | --- |
| paid | submitting / uncertain; fulfilled с тем же receipt идемпотентен | Подтверждение существующего orderNumber, расход резерва один раз, одна purchase-транзакция. Отдельно продолжается сверка товара. |
| rejected | submitting / uncertain | Только окончательный отказ и отсутствие будущей выдачи/окончательное урегулирование supplier debit: возвращается исходный резерв, заказ cancelled, решение и аудит. |
| refunded | fulfilled | Только подтверждённый полный возврат поставщика и прекращение выдачи: проверяется исходная purchase-транзакция, создаётся одна компенсирующая refund-транзакция, заказ cancelled; credentials больше не выдаются. |

Для rejected подтвердить, что поставщик не списывал средства либо полностью вернул
их, а выдача окончательно прекращена. Для refunded подтвердить полный supplier refund.
Частичные возвраты не поддерживаются: оставлять на ручной сверке, не применять этот API.

Один decision_id с неизменным телом повторяется безопасно, включая после перезапуска.
Изменение тела, несовпадение суммы/receipt, повтор результата с другим decision_id,
неверный переход или чужая роль отклоняются. Order/wallet/ledger/решение/аудит меняются
в одной транзакции; savepoint исключает частичный возврат при отказе. История claims
сохраняется после возврата. Никаких ручных UPDATE балансов или повторного release
для submitting/uncertain не нужно. Неподтверждённый результат оставляют без решения.

## Работающий бесплатный контроль

GitHub Actions **Proxy controlled verification process** → Run workflow.
Одноразовый localhost PostgreSQL, fake supplier, транспорт поставщика запрещён.
Помимо прежних 18 состояний, тесты `test_proxy_control` выполняют настоящий permit
flow при выключенном глобальном флаге и неизменном IPv6-only allowlist: автоматическую
выдачу, 90-секундную задержку, partial, timeout/manual, перезапуск, потерю процесса
после consumption, лимит/expiry/revoke/чужой UUID/чужого пользователя, параллельные
покупки и возвраты, paid/rejected/refunded с повтором решения. Это не настоящий платёж.
Три результата автоматической выдачи передаются настоящему ProxyOrders и проверяются
в браузере. JSON и screenshots сохраняются артефактом CI.

## Что останется сделать перед реальной проверкой

1. Выбрать конкретный заказ/сумму, получить отдельное разрешение владельца.
2. Создать один permit после этого разрешения; пользователь нажимает контрольную кнопку.
3. Проверить реальные непустые поля поставщика и подключение. Пока живой инвентарь был
   пуст, формат дат/metadata нельзя было подтвердить; неподдерживаемые данные останутся
   на ручной сверке без утечки credentials или повторной покупки.
4. При неопределённости использовать описанное финансовое решение только после
   подтверждения поддержки. Общие продажи не включать автоматически.

Этот документ заменяет пункты о недостающем refund API и UUID-ограничителе в протоколе
PR #88. Они больше не являются незавершёнными программными задачами.
